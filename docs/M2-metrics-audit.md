# M2.1 度量审计（离线，基于 M0 日志里游戏真实的 maxW 约束）

> 历史审计结果。近似度量脚本已删除；当前生产测宽和真实机器码回归见 [单行渲染说明](single-line-render.md)。

工具：`tools/audit_metrics.py`（把日志里每条 `BitFont::GetTextDimension` 的原文与 `maxW`
重放一遍，分别用"引擎自己的宽度字节"和"矢量 advance"累加，看是否超出调用者给出的上限）

```
310 条测量，字重 700，拉丁 13px / 中文 16px

Metrics=vector（完全自然度量）  总宽 = 1.377x   超框 1 条 (0.3%)
Metrics=scaled AdvanceScale=1.05 总宽 = 1.031x   超框 0 条 (0.0%)   ← 采用
Metrics=scaled AdvanceScale=1.10 总宽 = 1.125x   超框 1 条 (0.3%)
Metrics=scaled AdvanceScale=1.15 总宽 = 1.174x   超框 1 条 (0.3%)
Metrics=scaled AdvanceScale=1.20 总宽 = 1.205x   超框 1 条 (0.3%)
```

结论：

* 完全矢量度量会让文本整体宽 ~38%，对这套按点阵字体手工摆好的 UI 太激进；
* **+5% 步进是"零溢出"的最大档位** —— 格子变宽 → 压缩变轻 → 笔画随之变实，正好治标；
* 唯一会在 +10% 以上冒出来的界面是 `caller=0x00553199`（任务目标框，`maxW=400`）：
  自然度量下 451px / +13%，属于"换行位置变化"，需要单独处理（M2.2 逐界面适配）。

后续 M2.2 若要推进到自然度量，需要处理的清单就只有这一处（外加若干 `maxW=168` 的侧栏提示，
当前仍在阈值内）。
